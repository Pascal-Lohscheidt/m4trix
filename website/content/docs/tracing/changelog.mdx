### Breaking changes

- production-safe tracer that records cost, sessions and scores (`tracing`) **BREAKING** ([bd3c767](https://github.com/Pascal-Lohscheidt/m4trix/commit/bd3c7677b704a5ef44fe408b577966f4b690fd9f))

  The tracer never throws into the app and records much more per run. Upgrade notes are in the
  package README (\"Upgrading to 0.12\"); no storage migration is needed.
  
  - Failures go to `onError` and `tracer.stats()` instead of rejecting; traces flush on their own
    once their last run ends, failed flushes are retried, and buffered runs are bounded
    (`maxBufferedRuns`).
  - Payloads are capped (`maxPayloadBytes`) and redactable (`redact`); payloads with cycles,
    BigInts or Errors are stored safely.
  - Sampling (`ratioSampler`, `parentBasedSampler`), W3C `traceparent` propagation and an
    OpenTelemetry export (`@m4trix/tracing/otel`).
  - Model calls record the served model, provider, token details (cache reads and writes,
    reasoning) and time to first token; `priceTable` / `costOf` compute cost.
  - Traces carry `sessionId`, `userId` and `tags`; errors carry stack, status, code and cause;
    scores can be attached as annotations (`scoreAnnotationPatch`, `readScores`).
  - `toM4trixTracer` records cancelled runs with status `cancelled` and `ctx.reportUsage()` calls
    as LLM runs, and follows the @m4trix/core 0.18 tracer hooks.
  
  BREAKING CHANGE: `flush()` no longer rejects (use `onError`); `toM4trixTracer` records a
  network's context id as `sessionId` instead of `projectId` (pass `{ projectId }` to set one);
  run tags move from `run.extra.tags` to `run.tags`; `TraceStatus` gains `'cancelled'`.

  Waterfall: the run tree gets a time column. Each run shows a bar
  positioned on the trace's timeline (earliest run start to latest run
  end), coloured by run kind (LLM, tool, chain, other; errors rose), with
  a right-aligned duration. A sticky axis with nice-step ticks and grid
  lines sits above the rows. Unfinished runs extend to the end of the
  timeline and pulse; runs outside the window are clamped. The column
  width uses container query units so it lines up at every nesting
  level. A Waterfall | Tree toggle on the card switches back to the
  plain tree with full run names; waterfall is the default.
  
  Plumbing: the LangGraph plumbing pattern (ChannelWrite&lt;…>, Branch&lt;…>,
  __start__, __end__) moves to src/shared so the UI and the MCP
  get_trace outline hide the same runs. First-time users start with a
  \"LangGraph plumbing\" hide group; users with saved groups get a one-click
  \"Hide LangGraph plumbing\" chip instead. Hide groups no longer hide
  error runs, matching the MCP rule that a filter cannot mask a failure.
  
  URL state: trace, run and view live in the query string
  (?trace=…&run=…&view=tree), so reloads and shared links land on the
  same run. Selecting a trace pushes a history entry (Back returns to the
  previous trace and run); run and view changes replace it. A linked
  trace that is not in the sidebar list stays selected; it is only
  cleared when the list filters exclude it. The tree hook now drops the
  previous trace immediately, so a stale tree never pairs with a new
  selection.
  
  Also fixes the anime.js easing: v4 removed string easings, so
  'cubicBezier(...)' logged a warning per animation and fell back to the
  default curve. It now passes cubicBezier() from animejs.

  The viewer server now exposes the trace MCP as a Streamable HTTP
  endpoint at /mcp, next to the UI. Coding agents connect to the running
  viewer by URL instead of spawning their own process with a trace path:
  
      claude mcp add --transport http m4trix-traces http://127.0.0.1:4319/mcp

    so payloads loaded by one call stay searchable for later calls and
    for other agents.

    cross-site requests).

    startTraceViewerServer. The startup log prints the endpoint URL.
  - New exports: createTraceMcpHttpHandler, isAllowedMcpRequest,
    MCP_HTTP_PATH. createTraceMcpServer accepts a shared `tools` instance.
  - The stdio `mcp --path` subcommand remains for clients without HTTP
    support.
  
  Docs: the README and --help now lead with the HTTP setup and fix the
  stdio example, which used `npx m4trix-trace-viewer`, an npm package name
  that does not exist, instead of `npx -y @m4trix/trace-viewer`.

  high trace rates. projectId and time ranges were filters, so a selective query
  could read the whole index to fill one page.

    trace upsert.

    from the environment (e.g. maxConcurrentWrites), which it used to drop.

  indexes as sparse, like the real engine. It caught an unused `#listSk`

- let the sidecar clean up shipped traces on local disk (`tracing`) ([f9fe143](https://github.com/Pascal-Lohscheidt/m4trix/commit/f9fe143dfd2a331514b4eb06244ec9ac19d60e5d))

  The sidecar deleted payloads after upload but kept trace.json/runs.ndjson and
  the trace folders forever, so the shared volume (often an emptyDir) kept
  growing with every trace.
  
  After each pass, a trace folder is removed once it is fully replicated: every
  structure file was shipped at its current mtime, no payload is left, nothing

    judged by the folder's own mtime.
  - `--keep-shipped` turns cleanup off. Library users opt in through
    `TraceShipperDeps.retention`; omitting it keeps everything.
  - Durations now also accept hours (`24h`). Pass results report
    `removedTraces`, and cleanup errors land in `failures` like other items.

- add MCP server for coding agents (`trace-viewer`) ([18ee995](https://github.com/Pascal-Lohscheidt/m4trix/commit/18ee9958e3246bda49e5809cabc26bcc48203cd6))

  Add an `mcp` subcommand to the trace viewer CLI that serves the trace
  store as a local Model Context Protocol server over stdio, so coding
  agents can inspect, search and compare traces while debugging.
  
      claude mcp add m4trix-traces -- \\
        npx m4trix-trace-viewer mcp --path \"$PWD/tmp/tracing-example\"
  
  It reuses the viewer's storage adapters (`--adapter fs | aws-stack`).
  
  Tools:
  - list_traces: newest-first traces filtered by status, project, name,
    metadata, time range, latency and annotation
  - get_trace: run tree as a compact outline; LangGraph plumbing spans are
    hidden by default and error runs are never hidden
  - find_runs: runs by type, name, status, error text, latency, tokens or
    metadata across traces, without loading payloads
  - get_run: ancestry, timing, full error, children and payload previews
  - get_payload: payload as outline or JSON, narrowed by JSONPath, paged
    by offset
  - load_trace_payloads: load payloads into an in-memory search index;
    payloads are immutable, so reloads only fetch new refs; LRU eviction
  - search_payloads: text/regex search; identical values are grouped and
    attributed to the run where they first appeared (inputs at run start,
    outputs at run end) with its ancestry
  - analyze_trace: root-cause errors, unfinished and orphan runs, critical
    path and self time, token hotspots, repeated identical calls, and
    error-like values in successful runs
  - get_conversation: chat transcript for OpenAI, Anthropic and LangChain
    message shapes, including tool calls
  - compare: diff two runs field by field and payload by payload, or
    align two traces run by run
  - annotate: write trace/run annotations; the tool description asks
    agents to get the user's permission first
  
  Trace ids accept \"latest\" or a unique prefix, and run ids a unique
  prefix. Strings holding serialized JSON are decoded so paths and search
  reach into tool arguments. Every response has a size budget and says how
  to fetch the rest.
  
  The programmatic API exports createTraceMcpServer,
  startTraceMcpStdioServer and TraceTools.
  
  Note: the CLI now rejects unknown positional arguments (previously
  ignored) and accepts `serve` (default) or `mcp`.
  
  Co-Authored-By: Claude Opus 5.5 (1M context) &lt;noreply@anthropic.com>

  The Tracer kept every run it had ever seen and, on every callback, rebuilt the
  trace summary by scanning all of them. A long-lived tracer grew without bound
  and slowed down quadratically: 10,000 callbacks on one 5,000-run trace took

- stop the sidecar from stranding traces and crash-looping (`tracing`) ([f309818](https://github.com/Pascal-Lohscheidt/m4trix/commit/f30981801b3e24c8744f45e8933c51918264eace))

  A transient S3 error part-way through a pass left a trace stuck forever: the
  payloads uploaded earlier in that pass were already deleted locally, but the
  state recording them was only saved at the end, so the runs that referenced
  them never qualified for upload again. A single bad item (malformed file,
  oversized DynamoDB item) also failed every pass and crash-looped the
  container, state.json was written non-atomically, and shutdown skipped
  whatever the app flushed last.
  
  - A payload now counts as pending exactly while its local file exists.
    Payload refs are no longer kept in state, which also stops state.json from
    growing without bound. Old state files and already-stranded traces recover
    on the next pass.
  - Each item is attempted on its own. Failures are reported in
    `result.failures`, logged by the CLI and retried on the next pass, and no
    longer block other traces.
  - runs.ndjson is read once per ship, so the payload refs checked are the ones
    shipped.
  - State is written atomically, and an unreadable state file triggers a safe
    re-ship instead of a permanent failure.
  - The loop survives failed passes (reported via onError). After SIGTERM or
    SIGINT it makes one final pass before exiting. `--once` exits non-zero when
    any item failed.
  - Annotations are stripped before shipping, so the sidecar never overwrites
    review edits made in the hosted store.

- keep DynamoDB annotations safe from ingest and read whole traces (`tracing`) ([43dbf02](https://github.com/Pascal-Lohscheidt/m4trix/commit/43dbf0279900d2fa4ba92214635b7f6887f546c2))

  Ingest replaced whole items with PutItem, so any re-ship of a trace (a later
  write, or the sidecar's state being reset) wiped annotations made in the
  hosted viewer. Annotation patches were unconditional read-modify-writes, so
  concurrent reviewers overwrote each other. getTrace ran a single Query and
  silently returned a partial trace once its runs exceeded one 1 MB page.

    `annotationVersion` counter. Ingest uses UpdateItem to SET only
    `trace` / `run` (plus the GSI keys), so it never touches annotations.
  - Patches are version-checked conditional updates, retried on conflict and
    failing loudly after repeated conflicts. They also migrate annotations that
    0.8.0 stored inside `trace` / `run`; reads fall back to that location.
  - getTrace follows LastEvaluatedKey across pages.
  - upsertRunBatch caps concurrent writes (maxConcurrentWrites, default 16)
    instead of firing one request per run at once.
  
  Ingest now needs dynamodb:UpdateItem instead of dynamodb:PutItem.
  
  The spec's mock client is replaced by a fake that evaluates the SET/REMOVE and
  condition expressions and rejects unknown or unused placeholders like
  DynamoDB. The adapter was also checked against dynalite, including real
  1 MB query paging.

- serialize flushes and keep annotations on the filesystem store (`tracing`) ([24aa2ad](https://github.com/Pascal-Lohscheidt/m4trix/commit/24aa2add9bdbf879dc42f3600eb4b537da0bcac3))

  Overlapping Tracer.flush() calls (e.g. parallel agents ending through
  toM4trixTracer) raced on the read-modify-write of runs.ndjson and lost runs
  (16 of 31 in a reproduction). A failed flush also dropped its pending records,
  and every flush rewrote trace.json/runs.ndjson without annotations, wiping
  reviews added while a trace was still running.
  
  - Tracer.flush() now runs flushes one at a time, so an older snapshot can never
    land after a newer one, and re-queues records when a store write fails
    (without replacing newer versions queued meanwhile).
  - FsStructureStoreAdapter runs every read-modify-write of a trace under a
    per-trace lock (new KeyedMutex), and upserts that omit `annotation` keep the
    stored one. An explicit `annotation` on an upsert still replaces it.
