Write logic first. Wire it second.

Most frameworks make you draw a graph before you write a line of code. m4trix doesn't.
Agents declare what events they care about. The network figures out the rest at runtime.

The six primitives below compose into any topology — a linear chain, a fan-out, a multi-tenant swarm. You never redraw a graph when requirements change; you change which channel an agent subscribes to.

⚡

Event-Driven Agents

Write a typed async function. Tell the factory which events trigger it and which it can emit. No base class, no decorator, no node to register — just logic and a schema.

AgentFactory.run().listensTo([evt]).logic(fn).produce({})core
🔗

Agent Networks

setup() is the only wiring ceremony. Subscribe an agent to a channel, tell it where to publish. Chain, fan-out, fork — always the same two lines.

AgentNetwork.setup(({ registerAgent }) => …)core
🛡

Typed Events

The payload you emit in AgentA is the typed triggerEvent in AgentB. Effect Schema validates every handoff at runtime — a schema mismatch fails loudly, not silently in production.

AgentNetworkEvent.of('request', S.Struct({…}))typesafe
📡

SSE Streaming

Call .expose() on a network and you have a streaming HTTP endpoint. The Next.js adapter is a one-liner. Your frontend reads a Server-Sent Events stream, not a polling loop.

NextEndpoint.from(network.expose({…})).handler()stream
🔀

Channels & Sinks

Channels are named message buses. Swap an httpStream sink for Kafka without touching a single agent. The agent doesn't know — or care — where its events go.

createChannel('client').sink(sink.httpStream())infra
📦

Batteries Included

useConversation() manages SSE state in React. Pump chains transforms over streams. AiCursor renders a live typing indicator. Nothing to assemble separately.

@m4trix/evals

Repeatable evals for AI agents

Define datasets, evaluators, and test cases as TypeScript files. The CLI discovers and runs them by convention — like Vitest, but for your AI outputs.

*.dataset.ts *.evaluator.ts *.run-config.ts *.test-case.ts

Get Started → View on GitHub

Stop guessing. Define what good looks like.

You improved the prompt. But better by how much, versus which baseline, on which inputs?
Without a structured harness, every eval is a vibe check that you can't reproduce tomorrow.

The six primitives compose into a full eval pipeline: define your inputs once as TestCases, group them into Datasets by tag, score them with typed Evaluators, aggregate Metrics across repetitions, and run the whole thing from the CLI without wiring anything manually.

📊

Dataset

A named, tagged slice of your test cases. Run only the 'edge' tag before a hotfix. Run the full suite before a release. Same eval files, different scope — no duplication.

Dataset.define({ name: 'my-dataset', includedTags: ['core'] })define
🧪

Evaluator

A typed scoring function that knows its own context: the current run ID, which repetition it's on, how long the previous step took. All of that is in meta — no global state, no thread locals.

Evaluator.define({ name, evaluate: async ({ input, meta }) => … })score
📋

Test Cases

Stable named inputs with tags. The same 'user-asks-ambiguous-question' case feeds five different evaluators. Add a new evaluator next month and it picks up all existing cases automatically.

TestCase.define({ name, input: {…}, tags: ['edge'] })define
⚙️

Run Config

Wire a Dataset to its Evaluators. Set repetitions: 5 to measure variance. Set a seed to make sampling reproducible across runs. The RunConfig is what the CLI actually executes.

RunConfig.define({ name, rows: [{ dataset, evaluators }] })run
📐

Metrics

latencyMetric and scoreMetric ship out of the box. Defining a custom one is three lines: an id, a format function, and an optional aggregate. Results roll up across repetitions automatically.

Metric.of({ id, format: (v) => `${v}ms`, aggregate: avg })score
🖥

CLI Runner

Drop files under src/. The runner finds *.dataset.ts, *.evaluator.ts, *.run-config.ts, builds the execution plan, and reports. No registration file, no config beyond the naming convention.

pnpm m4trix-evals run --config m4trix-eval.config.tscli

Trace everything. Send it nowhere.

LangSmith has a pricing page. m4trix/tracing has a folder. Drop in a callback handler and every run lands in ./.traces on your machine — structured, queryable, and fully yours. No account. No upload. No cost per token. When you're ready to review, the same store that wrote the traces reads them back.

🔭

Drop-in Adapter

Already using LangGraph or LangChain? Pass the adapter in and the rest of your code doesn't change. One line to start capturing every model call, tool invocation, and chain step.

Tracer.from(store).adapt(toLangGraph)adapter
🗄

Split Storage

Structure (run metadata, timing, status) lives in small queryable rows. Payloads (prompts, completions, embeddings) live in blob refs. Query the small stuff fast — fetch the large stuff only when you need it.

TraceStore.from({ structure, payload })storage
🔍

Read What You Wrote

The same store that captured your traces serves them back. Reconstruct full trace trees, diff runs, surface failures — no separate read replica, no sync lag, no eventual consistency.

TraceViewerApi.from(store).getTraceTree(id)api
💾

Stays on Your Machine

File-based adapter out of the box. No sign-up, no API key, no data leaving your laptop. Traces land in a folder you control — read them with the viewer or grep them directly.

FsStructureStoreAdapter.from({ dir: './.traces' })local
🐳

Docker-native

In CI or a container environment? Mount a volume and both the agent and the viewer share the same path. No networking required — the filesystem is the bus.

docker run -v ./traces:/traces m4trix/trace-viewerops
✏️

Human-in-the-Loop

Annotate any run with a label and a note. Build review workflows where a human signs off on model behaviour before the next iteration ships — all from the same store, no third-party tool required.

api.patchRunAnnotation(runId, { label, note })review
